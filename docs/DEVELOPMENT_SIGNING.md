# Refresh local development signing

`tools/refresh-development-signing.py` automates the existing local signing
workflow. It reuses suitable cached profiles; if either main/helper profile is
missing, expired, or does not cover the selected certificate/team/device, it
invokes `xcodebuild -allowProvisioningUpdates
-allowProvisioningDeviceRegistration` once with the actual device destination.
It then re-signs a disposable copy using `tools/resign-app.py` and verifies the
deep strict signature. Optional installation upgrades the existing idle app
and reads back its bundle version. It does not launch the app or enable JIT.

Prerequisites:

- Xcode has an authorized account/session, its signing identity's private key is
  accessible, and Apple's provisioning service is reachable. A password, 2FA or
  keychain authorization prompt must be completed by the user. The script does
  not modify keychain settings or handle credentials. `No Accounts` alone does
  not establish that the Xcode GUI account is logged out.
- Supply a resource-complete `.app` from the intended build. The input is never
  modified. Preserve the installed bundle ID and signing team when upgrading to
  retain app data; the script does not rename bundles or uninstall anything.
- If profile renewal invokes a build, the repository's normal build resources,
  SDK/toolchain environment and dependencies must be available. Renewal can
  fail even though an unsigned app has already compiled. A profile generated by
  Xcode is independently checked before being used.
- Use the physical device UDID. An iPad-only profile cannot sign an iPhone app.
  Both the main app and `MadeiraJITHelper` need valid, exact profiles with
  `get-task-allow`. No ungranted entitlement can be added by re-signing.

Read-only check (no renewal, signing, installation or work-directory creation):

```sh
python3 tools/refresh-development-signing.py \
  --app /private/path/unsigned/Madeira.app \
  --device YOUR_IPHONE_UDID --team YOUR_TEAM_ID \
  --identity YOUR_EXISTING_CERTIFICATE_SHA1 \
  --work-dir /private/path/signing-artifacts --check-only
```

Remove `--check-only` to refresh profiles if needed and sign a private copy.
Add `--install` to upgrade the existing app after saving and closing it. The
script refuses installation while that app or its helper is running; it never
terminates them. It does not perform first installs. `--keychain` can select an
existing keychain; the default is `~/Library/Keychains/login.keychain-db`.
`--derived-data` can reuse an existing build directory for the renewal attempt.

Keep the work directory outside the source checkout. It contains the signed
app, private Xcode logs, provisioning profiles and device receipts. Never commit
or publish these files. Host tests use synthetic profiles and mocked process
lists; their success is not proof of Apple renewal, installation, JIT or Steam
gameplay. No recurring task is installed by this tool.

Apple documents [automatic signing](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices)
and [Personal Team limits](https://developer.apple.com/help/account/basics/about-your-developer-account).

Observed on this development machine: background `xcodebuild` returned
`No Accounts` while the GUI visibly retained the existing account/team. Normal
GUI automatic signing for the exact main/helper identifiers with the iPhone
selected generated suitable profiles; the script then successfully reused them
for re-signing and deep strict verification. This is not proof of unattended
profile renewal, installation or runtime success.

## Official background-build interface: prepared, not yet authorized

The installed Xcode27 scripting dictionary (`Contents/Resources/Xcode.sdef`)
defines a workspace `build` action and a scheme-action result with completion,
status and build errors. A narrowly scoped private helper can target the exact
signing workspace, scheme and physical device without sending UI keystrokes.
It refuses an overlapping build. Syntax compilation alone is not an actual
background build or profile-renewal result.

On2026-10-31 the normal Apple-event permission preflight, with consent prompting
disabled, returned -1744: authorization would require user consent. No helper
was executed through that interface and no permission/settings/database was
changed. Use a normal OS authorization flow before adopting this route; never
extract account credentials or assume Accessibility permission also authorizes
Apple events. The already-authorized GUI signing route remains distinct.

An ongoing task may use a bounded, one-shot native lock-state check to dispatch
the authorized GUI build immediately after a real user unlock. It performs no
UI action while a lock is known, has a fixed timeout and is not a recurring
automation. Record whether a build was actually requested, rather than treating
an unlock message or a timeout as proof. A temporary sleep assertion does not
establish that the system cannot lock again.
